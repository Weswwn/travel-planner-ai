# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An AI-assisted travel itinerary planner. Very early-stage / experimental. A step-by-step wizard collects trip-level info (country — US or Canada only, city, starting location/hotel address). The user then picks how to plan: **day-by-day** (add day tabs one at a time, fill in each day's date, already-made reservations, and considered places, generate each day's route on demand) or **AI-allocated** (give a day count, start date, and one pooled reservations+places wishlist for the whole trip; one cheap Claude call distributes the pool across days — no routing yet — landing the user on the same day-tabs UI, pre-filled per day, still generating each day's real route on demand; a "Redo AI planning" action re-opens that flow pre-filled with the same pool). Per day (either path), Claude plans an efficient order of visits respecting that day's reservation times; OpenRouteService geocodes each stop and computes the actual driving route; the frontend renders it on a Leaflet/OpenStreetMap map.

## Commands

- `pnpm dev` — start the Vite frontend dev server (localhost:5173)
- `pnpm server` — start the Express/Claude backend with `tsx --watch` (localhost:3001), loading env vars from `.env.local` (`NODE_ENV=local` → `.env.local`)
- `pnpm server:mock` — same, but with `MOCK_ITINERARY=true`: skips the real Claude + OpenRouteService calls (Claude has no free tier - it's pay-per-token; OpenRouteService is rate-limited on its free tier) and replays `server/mock-response.json`, a captured real response. Use this while iterating on the frontend so repeated testing doesn't burn quota/cost. Mock mode doesn't even require `ANTHROPIC_API_KEY` to be set - the Claude client (`server/claude.ts`) is only constructed lazily, inside the non-mock branch of each handler.
- `pnpm server:ollama` — same, but with `LLM_PROVIDER=ollama`: routes the two AI calls to a local Ollama server (`http://localhost:11434` by default; `OLLAMA_BASE_URL` to override) instead of Claude, using the `OLLAMA_MODEL` env var (defaults to `llama3.1`) — real AI-generated responses with zero API cost, at lower reasoning quality than Claude. Requires Ollama installed and running (`ollama serve`) with that model pulled (`ollama pull llama3.1`). Also needs no `ANTHROPIC_API_KEY`.
- `pnpm build` — type-check (`tsc -b`) then build the frontend with Vite
- `pnpm lint` — run ESLint over the repo
- `pnpm format` — run Prettier (write mode) over the repo
- `pnpm preview` — preview the production frontend build

Both the frontend (`pnpm dev`) and backend (`pnpm server`) need to be running for the app to work end-to-end — the frontend calls the backend at `http://localhost:3001`.

There is no test setup in this repo currently.

## Environment variables

Set in `.env.local` (gitignored):
- `ANTHROPIC_API_KEY` — used server-side by `server/claude.ts`. Only required when `LLM_PROVIDER` is unset/not `ollama` (i.e. real Claude generation) - pay-per-token, no free tier; get a key at console.anthropic.com (separate product/billing from a claude.ai subscription).
- `LLM_PROVIDER` — optional, set to `ollama` to use a local Ollama server instead of Claude (see `pnpm server:ollama` above). Unset or any other value uses Claude.
- `OLLAMA_MODEL` / `OLLAMA_BASE_URL` — optional, only read when `LLM_PROVIDER=ollama`; default to `llama3.1` and `http://localhost:11434`.
- `OPENROUTESERVICE_API_KEY` — used server-side by `server/index.ts` for OpenRouteService geocoding (`/geocode/search`), driving directions (`/v2/directions/driving-car/geojson`), and route optimization (`/optimization`). Free, no billing/credit card required — sign up at openrouteservice.org.
- `GEMINI_API_KEY` — leftover from before the Gemini→Claude swap; unused, safe to remove.
- `VITE_GOOGLE_MAPS_API_KEY` — currently unused (leftover from an earlier Google Maps-based implementation); safe to leave unset.

The backend loads env vars via `dotenv.config({ path: \`.env.${process.env.NODE_ENV}\` })`, so `NODE_ENV` must be set (the `server` script sets it to `local`) for `.env.local` to be picked up.

## Architecture

Two separate runtimes, no shared server framework:

- **`server/`** — Express API (run with `tsx`, not compiled separately). `server/llm.ts` is the single entry point both routes call for AI generation: `generateStructured(prompt, zodSchema)` returns a parsed-and-validated object matching the schema (or `null`), regardless of provider - it dispatches to `generateWithClaude` (uses `server/claude.ts`'s lazily-constructed Anthropic client + `client.messages.parse({..., output_config: {format: zodOutputFormat(schema)}})`, Claude's equivalent of the old Gemini `responseSchema`) or `generateWithOllama` (POSTs to a local Ollama server's `/api/chat` with `format: z.toJSONSchema(schema)` - Zod v4's built-in JSON Schema export, so both providers share the exact same schema definitions - then validates the response with `schema.safeParse` since local models are far less reliable about strictly honoring a schema) based on the `LLM_PROVIDER` env var. Both routes build a prompt string and call `generateStructured`, unaware of which provider is active:
  - `POST /api/itinerary` — single-day generation, accepting a `GenerateItineraryRequest` body (`server/types.ts`): `{ trip: {country, city, startingLocation}, day: {date, reservations, places} }`. Builds a prompt (grouping `day.places` into the 6 legacy buckets — breakfast/lunch/dinner/primaryActivities/secondaryActivities/lateNightActivities — and passing `day.reservations` as fixed-time constraints Claude must not reorder) to get back structured JSON (an ordered `route` of `{placeName, address, category, arrivalTime, ...}` — no lat/lng; LLMs are unreliable at recalling exact coordinates, so none is ever asked for). Then geocodes each place via OpenRouteService — appending `"{city}, {country}"` as disambiguating context for every stop except `startingLocation` — and requests a driving route between them (round trip), optionally reordering the flexible (non-reservation) stops via OpenRouteService's Optimization API for shortest distance (`optimizeStopOrder`, gated by the `optimizeRoute` request flag and the frontend's admin toggle) while pinning reservation stops at their scheduled position. Stops that can't be geocoded at all, geocode implausibly (`haversineKm` sanity check), or aren't reachable by car (`calculateRouteDroppingUnroutableStops`) are dropped and reported in `omittedStops` rather than failing the whole request. Responds with `{ itinerary, route: { geometry, stops, summary, omittedStops } }` (`GenerateItineraryResponse`).
  - `POST /api/itinerary/allocate-days` — multi-day allocation only, no geocoding or routing at all. Accepts `AllocateDaysRequest`: `{ trip, numberOfDays, startDate, places, reservations: [{name, date, time, notes?}] }` (reservations here carry an explicit date, unlike the per-day endpoint, since the caller already knows the trip's full date range). One Claude call distributes the pooled `places` across `numberOfDays`, using a `reservationSummary` (dates/times only, computed server-side via `addDays`) as balancing context so it doesn't overload a day that already has a fixed commitment — reservations themselves are matched to days by exact date equality in code, not by Claude. Responds with `AllocateDaysResponse`: `{ days: [{date, data: <6-bucket allocation>}] }`.
- **`src/`** — Vite/React 19 (RC) frontend, using Tailwind (`@tailwindcss/vite`) for the newer wizard/form components. `src/App.tsx` is a phase switch: `TripSetupWizard` (4-step: country → city → starting location → review) until trip info is set; then, if no days exist yet, either `PlanModeChoice` (day-by-day vs AI-allocated) or `AutoPlanWizard` (day count/start date → pooled wishlist → "Plan My Days", calling `allocate-days`); once days exist, `DayTabsBar` + the selected day's `DayPanel`, identical regardless of which path created them. All state lives in one hook, `src/planner/usePlannerState.ts` — critically, per-day generation state is keyed by day id at this central level (not inside the form component), so an in-flight `generateItinerary()` call still lands correctly even if the user has switched to a different day tab or the day was removed. The AI-allocated path never calls `generateItinerary` itself — `allocateDays()` only seeds each day's `input` (pre-filled reservations/places) with `generation: {status: "idle"}`, so the user still explicitly generates each day's real route one at a time, same as manual mode; this is deliberate (allocation is cheap, generation is not). `DayPanel` renders `DayInputForm` (reservations + categorized places, `day/ReservationsInput.tsx` / `day/PlacesInput.tsx` — the former has an optional `withDate` prop used only by `AutoPlanWizard`'s pooled reservations list) while a day is `idle`/`loading`/`error`, or `DayResultView` once `loaded` — the latter is the itinerary-list + `react-leaflet` map view (OSM tiles, no API key needed), rendering a `Marker` per stop and a `Polyline` for the route geometry (already `[lat, lng]` pairs from the backend). `src/Map/index.tsx` (`FitBounds`) fits the map viewport to the route; `src/Map/markerIcon.ts` builds numbered/colored SVG pin icons (not Leaflet's default raster icon).
- **Verified-place autocomplete**: `GET /api/places/autocomplete` (query `q`/`country`/`city`) proxies OpenRouteService's `/geocode/autocomplete`, biased with a server-cached city-center `focus.point` (`getCityFocusPoint`, backed by the existing `geocode()`) since country-boundary filtering alone ranks short prefixes badly. `src/day/PlaceNameAutocomplete.tsx` (debounced, min 3 chars) is used by `PlacesInput`, `ReservationsInput`, and the wizard's starting-location field. Selecting a suggestion attaches real `address/lat/lng` to that `ConsideredPlace`/`Reservation`/`TripInfo` entry; free-typing one doesn't. This exists because local LLMs (Ollama) reliably *hallucinate* fabricated street addresses for a bare place name rather than reconstructing the real one — confirmed empirically, same place name produced 3 different invented addresses across generations. `POST /api/itinerary` checks each stop (and the starting location) against these verified coordinates first and skips geocoding entirely when present, so a verified place's actual location no longer depends on what the LLM writes into its `address` field at all. Free-typed places still flow through the original LLM-address → `geocode()` path unchanged.
- The prompts (in `server/index.ts`) and Zod schemas are the source of truth for the itinerary JSON shape — `itinerary.json` and `server/response.json` are stale example outputs from an earlier Gemini-based prompt/schema version and won't match the current shape.
- Types are hand-duplicated between `server/types.ts` and `src/types.ts` (no shared build step between the two runtimes) — each file has a comment pointing at its counterpart; keep them in sync manually when the request/response shape changes.

Both `tsconfig.app.json` (frontend, DOM libs) and `tsconfig.node.json` (build tooling) are referenced from the root `tsconfig.json`; the backend under `server/` is executed directly by `tsx` rather than being part of either TS project's build.

## Notes for making changes

- `cors` origins in `server/index.ts` are hardcoded to `localhost:3001` and `localhost:5173`; update both if ports change.
- No persistence — trip/day state lives only in React state; a page reload loses everything. No "edit trip info after wizard" or "edit inputs and regenerate an already-loaded day" flows exist yet.
